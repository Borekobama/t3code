# 30-minute load soak, Mac mini (2026-11-12)

Completes the 30-minute requirement left open by the ~9-minute heavy window in
[compatibility.md](compatibility.md) ("Resources").

## Setup

Host: Mac mini, 12 cores, 16 GB RAM, macOS 15 (Darwin 24.6). Services untouched and running throughout:
`ai.openclaw.gateway`, `local.t3code-fork`, `com.iphonefleet.*`, `local.t3-backup`.

All generators started together at 16:49:13 and ran until about 17:19:30 (30 min 17 s wall clock):

| Generator | What it did |
| --- | --- |
| Sampler | `sample.sh 35`, every 30 s, 16:47:12-17:21:56 (72 rows). First 2 min were the baseline. |
| Build loop | `build-load.sh 30`: `provider-acp` tests plus `apps/server` ACP adapter tests, 40 rounds. |
| OpenClaw loop A and B | `openclaw agent --session-key soak-{a,b}-N --thinking low --timeout 300`, next prompt sent when the previous finished. |
| Claude Code loop | `claude -p ... --model claude-haiku-5-5` through `~/t3-fork/gui-run.sh` (keychain login), same pacing. |

Prompts: six tool-free "write a small Python module plus pytest tests, reply with code only" prompts, rotated.
Deviation from the brief: the session key got a suffix that changes every 8 turns (`soak-a-1`, `soak-a-2`, ...), so
the conversation context stayed bounded instead of growing for the whole run. The model for the OpenClaw loops was the
default (Sonnet 5.5, Claude CLI subscription). No T3 threads were created.

Compared with the earlier 9-minute run (3 agents plus T3 test loop): memory free min 77 % to 44 %, compressed max
1.2 GB to 5.6 GB, CPU max 47 % to 68 %, RSS max 6.7 GB to 10.0 GB. Swap stayed at 0 (`vm.swapusage` total 0 MB).
Memory use grew over the first 15 minutes and then plateaued around 60-65 % free.

Notes on the numbers:

- The idle baseline is short (2 min) and not truly quiet: other work (other sessions, fleet services) was active, so
  idle CPU is 12 %, higher than the 4 % in the earlier run.
- Lowest free memory (44 %, compressed 5.6 GB) was one sample at 17:07:16, during build rounds. Cause not isolated.
- T3 (`local.t3code-fork`) was restarted during the run: its process started at 17:10:48, and `last exit code = 130`.
  Another session probably deployed a build. The CPU maximum (68 % busy at 17:10:41) and load1 maximum (11.1 at
  17:11:10) fall right around that restart and are likely partly its cost. Excluding samples 17:10:30-17:12:30 (4 samples) the CPU max is 44 % (avg 24 %) and load1 max 6.6,
  I did not verify the cause. The gateway started at 16:30:57, before the soak, so it did not restart during the run.

## Errors and timeouts

None. All 296 agent turns exited 0 and none hit the 300 s timeout. The Python/pytest code in replies contains the
words "timeout" and "rate limit"; those are not errors. No rate-limit or overload messages from the subscription.

## Recommended concurrency for this mini (Apple M6, 16 GB)

- **Up to 3 concurrent agent turns (any mix of OpenClaw, Claude Code, Codex) plus one build/test loop and the existing
  services.** This is the tested ceiling: no swap, 44 % free at worst, CPU at 26 % average.
- 4 to 5 concurrent agents without Xcode is a plausible extrapolation (the agents are mostly waiting on the network and
  the CPU has headroom), but it was not measured here. Memory, not CPU, is the limit: compressed memory reached 5.6 GB
  and the baseline already carries about 4 GB of node/agent RSS.
- Treat 2 to 3 agents as the limit while Xcode, simulator or `xcodebuild` work is running. A large Xcode build and
  one or more simulators can use several GB and many cores. This soak did not include any of that, so measure again
  before adding them.
- Watch `memory_pressure` free % and swap. Reduce concurrency if free memory stays below about 30 % or swap starts
  to grow. Those thresholds are judgment, not measured limits.
- Each agent turn here was short (about 15-25 s, no tools). Long tool-using turns hold processes and memory longer,
  so real work can look heavier than this load.
